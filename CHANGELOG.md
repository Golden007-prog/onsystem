- [#201](https://github.com/dgesteves/onsystem/pull/201) [`ee231a8`](https://github.com/dgesteves/onsystem/commit/ee231a8a8c7a1afb09aea67e882bf10414c96dcd) - Tokens are read the way the stylesheets and the Tailwind config apply them, in four cases where they were not.
  
  - An `@theme` color that wraps a variable of bare channels, as shadcn/ui's Tailwind v4 codemod leaves a v3 theme (`--color-destructive: hsl(var(--destructive))` with `--destructive: 0 84.2% 60.2%`), is the token `destructive` with its class. The class and the color were on two tokens, so every fix was an arbitrary value: `text-red-500` was fixed to `text-[hsl(var(--destructive))]`, and now to `text-destructive`. `rgb(var(--x))` over RGB channels counts too. An `@theme` value that names another variable takes its color: with `--color-brand: var(--color-blue-600)`, `bg-blue-600` suggests `bg-brand`.
  - Stylesheets imported one after another apply as CSS applies them: a later `@import` overrides an earlier one, and the importing stylesheet's own rules override both. With `@import "./base.css"; @import "./brand.css";`, `--primary` came from base.css, so `bg-[[#171717](https://github.com/dgesteves/onsystem/issues/171717)]` was fixed to `bg-primary`, which renders brand.css's color.
  - A Tailwind v3 config that extends `borderRadius` (as shadcn/ui's does, with `lg`, `md` and `sm`), or sets none, keeps Tailwind's default scale: `rounded-[12px]` is fixed to `rounded-xl`, not `rounded-lg` (8px), and `rounded-b-[24px]` to `rounded-b-3xl`, not `rounded-b-full`. A `theme.borderRadius` outside `extend` replaces the scale, unless it spreads `defaultTheme.borderRadius` into it. No default step is added when the scale cannot be read: a step of the config has no known size, because no stylesheet read sets the variable it uses (`var(--radius)`); the config takes a preset, a theme or the whole config from an installed package (`presets: [require("@acme/preset")]`, `theme: require("@acme/theme")`, `module.exports = require("@acme/tailwind-config")`, `{ ...base, content }`), which may replace the scale; or `borderRadius` is set from a variable, a function or a spread other than `defaultTheme.borderRadius`. Tailwind's own modules (`tailwindcss/defaultConfig`) do not count. A `theme` that is a module of the project, or spreads one (`theme: require("./theme")`, `theme: { ...require("./theme") }`), replaces the scale with its own `borderRadius`, and `presets: []` leaves out Tailwind's default config, so neither keeps the default steps unless a `theme.borderRadius` spreads them back in. Nor is one added in a Tailwind v4 project that reads the config through `@config`, which has v4's scale. In a Tailwind v3 project with no radius tokens of its own, such as Dub, `no-hardcoded-radius` now runs against that scale, so `check` can report warnings it did not before.
  - When `components.json` names a stylesheet in another package, as cal.com's names coss/ui's, zero config also reads the app's own stylesheet first (`styles/globals.css`, `app/globals.css` and the others it looks for without `components.json`), and the named one through it when the app's stylesheet imports it. cal.com's own tokens (`text-subtle`, `bg-emphasis`, `rounded-cal`) were not read, and color fixes named coss/ui's tokens instead. When the app's stylesheet imports Tailwind v4, the spacing and radius rules use Tailwind's scale, as in any Tailwind v4 app.

- [#192](https://github.com/dgesteves/onsystem/pull/192) [`eeb3af0`](https://github.com/dgesteves/onsystem/commit/eeb3af0ea82c8441ec9f79f1b74ff71f3150f916) - The baseline follows a file that is renamed or moved. Its entries are keyed by path, so after `git mv` every finding of the file was new to `check .` and to the GitHub Action with `only-changed-lines: false`, and nothing was said about the entries left under the old path. Now a file with no entries of its own, new or not, takes over those of a file that no longer exists when at least half of its findings match them, and half of them match its findings, as git counts a rename from 50% similarity. A rename that changes only the case of a name counts too, also on macOS and Windows, where the old spelling still opens the file. `check` says which file it took for moved, and `--prune-baseline` records the new path. Each file that no longer exists is taken over by one file at most, so copies of a file are still new, and a finding the move adds is still reported. In the GitHub Action, a file the pull request did not change keeps the entries it took over, so a copy the pull request adds is the new one, even when the rename was merged without `--prune-baseline`; `check` alone prefers the file whose findings match the old entries most closely, then a file that kept the old name, then one in the old folder. The entries of deleted files in the folders a run checks now count in the "no longer occurs" hint.
  
  The GitHub Action tells `check` which lines a pull request changed, and the baseline accepts the findings on the other lines first. A pull request that copied a baselined line above the original passed before: the baseline accepted the copy, and the original, reported instead, was on a line the pull request did not change. Now the copy is reported, on the line it was added, and fails the check. `check` without the Action still accepts findings in file order.
  
  The GitHub Action runs the onsystem the project installed, found in `working-directory` or the nearest folder above it up to the repository root, so the version the lockfile pins checks the pull request, and the log says when it is not the action's own version. Without an install, it runs `npx onsystem@<the action's version>` as before. With an install, the action's results now follow the installed version, so this can change the result of a job that passed before: an older install can have fewer rules, and one older than this release accepts baselined findings in file order, whatever lines the pull request changed. A newer one can find more.
